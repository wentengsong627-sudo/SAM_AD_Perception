# A D 文字感知模块部署和接入指南

本说明写给接手感知模块的同学。我们的交付是：你输入“跟踪哪一个目标”，再不断送入相机或视频图像，模块不断返回目标在图像中的位置和轮廓。你可以选择 A 或 D，两者的输入和输出格式相同。

模型应当装在接收方自己的 NVIDIA 显卡电脑上。原 FlyCo 工程继续负责点云、三维预测、规划和执行；我们的模块负责提供它需要的二维目标掩码。先用视频确认模型能运行，再接入原工程，会更容易定位问题。

版本日期为 2026 年 10 月 29 日。建议第一次按本说明的顺序操作。

## 1 先弄清楚模块在做什么

### 一句话和一张图怎样变成轮廓

假设视频里有人和狗，你输入 `dog`。A 先用 Grounding DINO 把文字对应到图中的狗，得到目标框；再把框交给 SAM2.1，得到狗的像素轮廓。后面的帧主要由 SAM2 的视频记忆持续跟踪；出现异常或丢失时再搜索和验证。

D 使用 EfficientSAM3 的文字分割能力，逐帧根据文字生成候选掩码，再由我们的身份和状态逻辑决定是否接受。D 的连续身份来自应用层关联，它没有 A 的 SAM2 神经视频记忆。

| 项目 | A 方案 | D 方案 |
| --- | --- | --- |
| 文字对应图像 | Grounding DINO Tiny | EfficientSAM3 的文字编码与图像融合 |
| 生成掩码 | SAM2.1 Hiera Tiny | EfficientSAM3 TinyViT 11M |
| 连续帧 | SAM2 记忆与受控提交 | 逐帧分割与身份关联 |
| 共同逻辑 | 可信参考、候选复核、丢失状态 | 同样使用受控身份检查 |
| 常用描述 | dog、red car 等简短目标描述 | 简短英文，最多 14 个内容 token |

token 是模型切分后的文字片段，不等于 14 个汉字或 14 个单词。先用 `dog` 或 `car` 跑通。中文只支持应用内已经映射的常见表达，不是任意中文理解。现有 Paraformer 以后输出识别文字，再调用相同的文字接口即可；本次交付不包含语音识别服务。

### 输出和原图的关系

RGB 原图是 H×W×3 的彩色图；掩码是 H×W 的单通道图。两张图大小对应、像素位置对应，但它们是两个独立数据。我们通过 PNG 和 SDK 返回的掩码只有 0 和 255：0 是背景，255 是目标。需要 0/1 时写 `binary = (mask > 0).astype("uint8")`。

彩色覆盖图只是演示时把掩码画到原图上；它不是模型必须提供给后端的数据。目标被完全遮挡或证据不足时，`mask` 为 `None`，不能把预测位置当作真实可见轮廓。

### 当前交付的边界

每个服务进程只允许一个活动会话，每个会话只选择一个目标。这适配原 FlyCo 的单目标感知链路。历史网页中的多目标和“所有目标”功能没有作为本次 SDK 的承诺；调用 `all dogs` 会明确报错，不会悄悄变成单目标。

身份模板是轻量外观证据，不能保证在相似目标交叉、外观明显变化或长时间离开后认出原来那一只。无法确认时保持丢失，比错误替换目标更合适。

## 2 文件应该放在哪里

GitHub 位置：`wentengsong627-sudo/SAM_AD_Perception` 仓库根目录。下载仓库后，进入这一层目录再执行命令。目录名后面能看到 `start_A.ps1`、`prepare_assets.py` 和 `sam_ad`，就说明位置正确。

| 文件或目录 | 用来做什么 |
| --- | --- |
| sam_ad | 统一服务端接口与 Python 客户端 |
| runtime_api 和 runtime_app | A/D 模型适配与跟踪逻辑 |
| prepare_assets.py 和 assets.lock.json | 准备模型源码、权重并检查 SHA256 |
| start_A 和 start_D | 启动对应模型进程 |
| examples/video_client.py | 用视频逐帧调用和查看结果 |
| sdk | 供调用方安装的轻量客户端 |
| flyco_adapter | 安装到原 FlyCo 的感知适配器 |
| openapi.json | 每个 HTTP 请求和返回字段的定义 |

`models`、`sam2-official` 和 `third_party` 会在准备依赖后出现。它们不进入普通 Git 提交，但推理时需要保留。不要只把 `start_A` 一个文件发给同学。

### 为什么有两个进程和端口

原 FlyCo/ROS 和模型所需的 Python 版本不同，所以把模型放在独立进程里。两者通过本机 HTTP 交换图像和掩码，不必把模型依赖塞进原 ROS 环境。

`127.0.0.1` 表示“当前这台电脑”。`8850` 是 A 进程的端口，`8851` 是 D 的端口，相当于软件的门牌号。同一台电脑上的原 FlyCo 可以直接访问这个地址。本机 HTTP 不需要互联网，也不需要浏览器。

如果模型和 ROS 在不同电脑，或者处于不同容器中，`127.0.0.1` 指向的就不是同一个环境，需要配置可达地址。跨机器访问还需要设置至少 24 个字符的 `SAM_AD_API_TOKEN`，客户端携带相同 token；默认只监听本机。

## 3 第一次在自己的 NVIDIA 电脑安装

### 安装前检查

终端运行 `nvidia-smi`，应能看到 NVIDIA 显卡和驱动信息。运行 `python --version`，应使用 Python 3.12。模型服务使用独立 `.venv` 环境，不修改原 ROS 的 Python 3.8 环境。

当前实际验证主机是 Windows、RTX 5060 Laptop 8GB、Python 3.12.7、PyTorch 2.7.1 CUDA 12.8。Ubuntu 提供了安装和启动脚本，但此交付未在 Ubuntu GPU 上做完整运行验收。4090 可按相同 CUDA 路线准备，实际速度需要在那台机器测。

### Windows 安装

在 `SAM_AD_Perception` 目录打开 PowerShell，执行：

```powershell
.\setup_windows.ps1
```

脚本会建立 `.venv`、安装 PyTorch 和依赖、准备 A/D 的模型源码与权重，最后检查 CUDA 和文件完整性。如果默认的 `python` 不是 3.12，可指定实际路径：

```powershell
.\setup_windows.ps1 -Python "C:\实际路径\Python312\python.exe"
```

如果 PowerShell 提示禁止运行此脚本，可只对本次启动使用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\setup_windows.ps1
```

### Ubuntu 安装

先确保已安装 Python 3.12 和对应的 venv 支持，再进入模块目录执行：

```bash
bash setup_linux.sh
```

运行原 FlyCo 时仍使用它原有的 ROS Noetic 环境；模型服务另开终端启动。不要用模型安装脚本替换原 FlyCo 的系统 Python。

### 模型下载和离线使用

A/D 所需权重合计约 1.25 GiB，另需 Python、PyTorch 和其他依赖的磁盘空间。第一次联网准备可能比较久。脚本从原作者来源下载，按 `assets.lock.json` 的文件大小与 SHA256 核对，不接受名称相同但内容不同的权重。

已经拿到旧的完整模型包时，可以先从包中准备依赖，避免重新下载。这里填解压后的目录，不是 ZIP 文件：

```powershell
python prepare_assets.py --from-bundle "D:\交接包\SAM_AD_Module_20261027"
```

只安装 A 可以使用 `setup_windows.ps1 -Backend A`；Ubuntu 对应 `bash setup_linux.sh A`。只装 D 时将 A 改为 D。默认安装两套，便于切换。源代码和模型依赖准备完毕、Python 环境也完整后，运行不需要互联网。GitHub 源码包不等于包含所有驱动和离线 pip 安装包。

## 4 先用一段视频跑通

### 启动 A

保留第一个终端运行模型服务：

```powershell
.\start_A.ps1
```

启动后打开 `http://127.0.0.1:8850/health` 查看状态。`loading` 表示模型在加载或预热，`ready` 才能开始任务，`error` 需要查看终端错误。预热会运行 8 帧合成图，不是视频只能处理 8 帧。

另开第二个 PowerShell 终端，仍在模块目录，使用你的视频实际路径：

```powershell
.\.venv\Scripts\python.exe examples/video_client.py --backend A --video "D:\videos\dog.mp4" --text dog --display
```

Ubuntu 启动用 `bash start_A.sh`，示例解释器改成 `.venv/bin/python`，视频路径也换成 Ubuntu 上的实际文件路径。

这个例子将视频缩放为 640×480，逐帧请求处理并显示覆盖轮廓；没有指定 `--max-frames` 就处理到视频结束。它按处理速度播放，不承诺与视频原始帧率一样快。正式程序可传入自己的分辨率，一次会话中保持尺寸一致。

### 换成 D

关闭视频示例，在 A 的服务终端按 Ctrl+C 退出。然后启动 D：

```powershell
.\start_D.ps1
.\.venv\Scripts\python.exe examples/video_client.py --backend D --video "D:\videos\dog.mp4" --text dog --display
```

这两条命令分别在模型终端和调用终端执行。D 的健康检查地址是 `http://127.0.0.1:8851/health`。比较时使用相同视频、文字、分辨率、帧数和显示方式；同时启动两个模型会相互占用显存，不能作为公平速度比较。

### 结果在哪里

默认 `client-output` 里有掩码 PNG、`events.jsonl` 和预览图 `last_frame.jpg`。先检查前景是否真的是指定目标，不能仅凭窗口有颜色就判断正确。`events.jsonl` 会记录状态和掩码数据，长视频会占用磁盘；正式集成可改为只保存必要字段。

## 5 在自己的程序里调用

### 最少需要写的代码

在模块目录运行时可以直接导入客户端。如果调用程序在另一个环境，给那个环境安装轻量 SDK；不需要安装服务端模型依赖：

```bash
python -m pip install sdk/sam_ad_client-1.0.0-py3-none-any.whl
```

调用数组与解码掩码需要调用方已有 NumPy 和 OpenCV。原 ROS 环境应保留原来的版本；不要把面向 Python 3.12 的依赖锁直接安装到 ROS Python 3.8。只传 PNG 字节、读取 PNG 字节时，SDK 的 HTTP 部分只依赖 Python 标准库。

```python
from sam_ad import Client

with Client("http://127.0.0.1:8850", backend="A") as sam:
    sam.wait_ready()
    sam.start("dog")
    while True:
        ok, frame_bgr = cap.read()
        if not ok:
            break
        result = sam.process_bgr(frame_bgr)
        if result.visible:
            mask = result.mask
            box = result.bbox_xyxy
            # 把 mask 送给你原来的点云投影或后续处理
        else:
            # 当前没有可靠可见目标，不提交旧轮廓
            print(result.states)
```

这里 `cap` 是你已经打开的视频或相机。OpenCV 读出来是 BGR，使用 `process_bgr`；如果你的相机输出已经是 RGB，就使用 `process_rgb`。用错颜色顺序会影响模型，不能只改变量名。

一次任务调用一次 `start`，之后每帧调用一次 `process`。不要每帧重新 `start`，那会反复清空身份与跟踪记忆。需要从狗换成车时再调用 `sam.start("car")`。离开 `with` 会释放会话。

### 怎样看返回值

| 返回值 | 通俗解释 | 调用方应怎么用 |
| --- | --- | --- |
| result.visible | 这一帧是否有可靠可见结果 | 先判断它，再消费掩码 |
| result.mask | H×W、uint8、0/255 或 None | 与当前帧像素对齐，独立于 RGB |
| result.bbox_xyxy | x1 y1 x2 y2 或 None | 像素坐标，右边和下边是排除边界 |
| result.states | 目标 ID 对应当前状态 | 用于提示跟踪或丢失，不能代替 visible |
| result.data | 完整 JSON 元数据 | 查看耗时、帧号、校验值与调用次数 |

例如框 `[10, 20, 50, 60]` 覆盖 `image[20:60, 10:50]`。框只描述二维位置，不是世界坐标。单独的掩码也不包含深度；深度来自你原系统的 LiDAR 或深度传感器。

### 丢失和异常时怎么做

状态包括 TRACKING 跟踪、SUSPECT 可疑、OCCLUDED 遮挡、LOST 丢失、REACQUIRING 正在找回、VERIFYING 待确认。待确认或丢失时可能仍保留原 ID，但这不表示目标当前可见。

SDK 自动管理从 0 开始的连续帧号。响应丢失时，同一帧可能已经被服务处理，SDK 保留待重试请求；使用 `retry_pending()` 重试原请求，不要直接跳到下一帧。收到明确错误时按错误处理，不要把失败帧当作成功掩码。

上层发现深度或几何不一致时，可调用 `sam.hint("depth_inconsistent")` 请求重新检查，它保留身份参考。`reset()` 则释放整个目标任务，二者含义不同。180 秒没有活动请求时，会话会过期。

## 6 替换原 FlyCo 的感知实现

### 先明确替换位置

数据流程是：原文字和 RGB 输入 → 我们的 A 或 D 感知实现 → 原格式掩码 → 原点云投影与聚类 → 原三维预测 → 原规划与执行。点云标定、消息定义、mesh_predict、planner_simulator 沿用原系统。

模型进程和原 ROS 在同一台 NVIDIA 主机上也可以运行。我们不要求把图像传到作者的笔记本，不需要运行历史演示网页。

### 第一步 准备原工程

接收方自己获取原 FlyCo 仓库并配置原有环境。自动安装器只接受下面这个已检查版本：

```bash
git clone https://github.com/FC-Family/FlyCo.git
cd FlyCo
git checkout 992ab2b6d193f79e45ae925497228ec45def67fc
```

这组命令用于新克隆的目录。已有工作目录如存在自己的改动，不要为了安装而直接切换或重置；先保留自己的工程，使用匹配版本的独立副本做接入检查。

原 FlyCo 许可证包含不得分发其软件副本的条款，因此这里不上传整套原仓库或整份修改后的原文件。适配安装器保存我们新增的文件与修改指令，在接收方本地的原文件上构建相同适配结果。

### 第二步 安装适配器

回到本模块目录，先检查，再安装。`/home/你的用户名/FlyCo` 换成实际原工程路径：

```bash
python3 flyco_adapter/install_into_flyco.py --repo /home/你的用户名/FlyCo --check
python3 flyco_adapter/install_into_flyco.py --repo /home/你的用户名/FlyCo
```

安装器会核对原仓库版本和每个待修改文件。发现本地改动会停止，不会强行覆盖。安装前的原文件保存在 `FlyCo/.sam-ad-backups/时间戳/`；重复安装同一个版本不会重复修改。原始仓库的来源与许可证保持独立。

### 第三步 启动模型和原感知节点

在模型自己的 Python 3.12 环境运行 `bash start_A.sh`，等到健康检查显示 ready。另开原 ROS 终端，按原 FlyCo 步骤编译并 source 工作空间，再执行：

```bash
roslaunch sam_tracking tracking_with_prompt.launch \
  segmentation_backend:=A \
  segmentation_endpoint:=http://127.0.0.1:8850
```

选择 D 时使用 `bash start_D.sh`，并把两个参数改成 `D` 和 `http://127.0.0.1:8851`。此处是单独感知节点接入检查，不会自动启动完整仿真世界。

另开同样已经 source ROS 环境的终端，发布原文字话题：

```bash
rostopic pub -1 /query_text std_msgs/String "data: 'dog'"
```

相机、点云和位姿话题仍需对应原仓库的实际配置与同步输入。没有这些数据，模型服务 ready 也不会凭空产生三维点云。原输出包括 `/sam_tracking/compress_mask_and_transform` 和 `/tracking/target_pointcloud`，名称可受原 launch 配置影响。

### 第四步 接回完整原系统

沿用原 FlyCo 的整体启动方式，在执行原入口前设置：

```bash
export FLYCO_SEGMENTATION_BACKEND=A
export FLYCO_SEGMENTATION_ENDPOINT=http://127.0.0.1:8850
```

使用 D 时改成 D 和 8851。适配代码将选择参数传入感知节点，后端仍是原工程。原 Linux Docker 入口使用 host 网络时，可以访问同机模型服务；Windows Docker 和不同网络环境不能直接照搬这个 localhost 假设，需要先验证地址互通。

## 7 不使用 Python SDK 时的 HTTP 接口

所有请求和返回使用 JSON。图像先编码成 PNG，再进行 Base64 编码放进 JSON。Base64 只是把二进制图片表示成文字，服务解码后仍得到原始图像尺寸；不要把 RGB 像素列表直接塞进 `image_png`。

| 方法和路径 | 发送什么 | 用来做什么 |
| --- | --- | --- |
| GET /health | 无请求体 | 查看加载状态和实际后端 |
| POST /session | text、owner | 开始一次目标任务 |
| POST /frame | session、sequence、image_png | 提交一帧并获得结果 |
| POST /hint | session、reason | 提醒当前结果可疑，保留身份 |
| POST /reset | session | 结束任务并释放状态 |

开始任务的请求例子：

```json
{"text":"dog","owner":"my-flyco-node"}
```

保存返回的 `session`，第一帧发送：

```json
{"session":"服务返回的编号","sequence":0,"image_png":"PNG的Base64字符串","timestamp_ns":0}
```

后续帧 sequence 按 1、2、3 递增。时间戳是可选的非负纳秒整数，只作为调用方采集时间回传，不会自动变成世界坐标或飞行速度。原始返回的 `mask_png` 是 Base64 PNG 或 null；SDK 的 `result.mask` 已经帮你解码成数组。

同一会话中图像尺寸必须一致。最大边长 4096、最多 8847360 像素，JSON 请求体上限 16 MiB；这是接收限制，不是性能承诺。重复最近一帧时，PNG 内容和时间戳必须完全相同，服务返回缓存结果，不会再推进记忆。

### 常见错误怎样处理

| 错误或现象 | 原因和处理 |
| --- | --- |
| Connection refused | 地址处没有服务；先检查服务终端是否仍在运行和端口是否一致 |
| health 显示 loading | 加载与预热尚未完成；等待 ready，不要反复重启 |
| CUDA unavailable | 驱动或 CUDA 版 PyTorch 不可用；本交付不自动退回 CPU |
| 409 | 会话冲突、帧号错误、图像尺寸变化或重复帧内容不同；按 error_code 排查 |
| 422 | 不支持的文字或所有目标请求；D 也可能是文字超过长度 |
| 503 | 模型未就绪或队列繁忙；控制调用速度，避免无限堆帧 |
| 504 或响应丢失 | 该帧可能已运行；SDK 使用 retry_pending 重试相同帧 |
| 一直没轮廓 | 看 visible 和 states，检查文字、颜色顺序、目标是否存在及服务日志 |
| out of memory | 先停止另一个模型和无关显存任务，再单独测；不要把两服务争用当作模型速度 |

不要一有丢失就调用 reset，否则固定身份参考也会被删除。正常恢复由模块持续尝试；如果目标一直不可确认，应保持无可靠观测并让上层按丢失处理。

## 8 如何确认接入成功

先确认 `/health` 的 backend 与选择一致，status 为 ready。再拿确实包含目标的视频，确认有多帧非空掩码，颜色覆盖在目标上，框和掩码位置一致。换 A/D 时保持其他测试条件不变。

接口回归命令是 `python -B tests/test_contract.py`。它使用明确的替身流水线验证帧序、重复请求、颜色、掩码、会话和错误处理，不证明模型识别正确。真实 CUDA 回放可运行 `tests/gpu_smoke.py`，具体参数见该脚本的 `--help`。本次发布的检查摘要在根目录 `validation.json`。

已完成的本机检查与完整工程验收需要区分：本机可以验证模型真实推理、协议和实际 FlyCo 核心回放；ROS 主节点、真实点云标定、Unreal、三维预测和飞行闭环，需要在接收方原系统运行确认。视频里输出了多少非空帧，也不能直接当成有人工真值的准确率。

最后交给同学时，给出仓库目录和本说明，让他在自己的电脑上完成“安装 → 视频测试 → 接原 FlyCo”。保留模型依赖目录、许可证与锁定清单。后续如果只想换模型方案，优先保持输入和输出协议不变，这样下游点云与规划代码才能继续使用。
